## Protocol and exact RPC arguments

All public wrappers are `SECURITY INVOKER`, with PUBLIC/anon/authenticated execution revoked and only service_role execution granted. Their private fixed-search-path functions are `SECURITY DEFINER` under the reviewed installer. API roles receive no access to auth.users or the journal. The installer must already have the auth id read/lock rights; the proposal does not grant those rights to clients. No routine is an authenticated caller-selected-UID deletion endpoint. The Edge service must first verify `getUser`, derive the UID from that result, verify its password through an isolated anonymous client and require the typed DELETE confirmation.

| --- | --- | --- |
| `mm_deletion_prepare_v1` | `user_id uuid` | Initial/expired pre-auth admission: `ok:true,status:reserved,job_id,lease_token,state`. Active lease: `busy` without token. | `mm_deletion_cleanup_v1` | `job_id uuid,lease_token uuid` | `ok:true,status:cleaned,counts` or a typed false/stale result. Cleanup errors throw so the whole SQL transaction rolls back. |

The journal state sequence is `requested -> cleaned -> auth_dispatched -> completed`, with `auth_unconfirmed` for uncertain Auth outcomes. A two-minute lease may be replaced only before Auth dispatch. An old token cannot clean, dispatch, finish or reconcile a new token's job. Auth-dispatched/uncertain work never becomes safe to reissue because a timer expired.

Operator `auth_present_retry` is an explicit attestation that the exact external subject state and the old Auth call's drainage/isolation were resolved. The SQL routine cannot establish external request cancellation. It is not an automatic retry or exactly-once Auth guarantee. A resolution ID is globally unique; conflicting/replayed resolutions cannot partially change journal state. Service-only recovery remains available after the original login has disappeared. Jobs deliberately do **not** cascade with auth.users. No retention interval is invented; the remaining subject UUID and bounded operational note are retained personal operational metadata requiring disclosure and a reviewed retention procedure.

## Atomic public cleanup and write admission

Admission obtains a per-subject advisory lock and an auth-user FOR UPDATE lock, then creates/claims the journal and commits. It does not modify public personal rows in that transaction. Public write triggers obtain auth-user KEY SHARE, then inspect the committed journal. Thus an earlier admitted writer finishes before deletion admission, and later writes observe its fence. Unsupported REPEATABLE READ/SERIALIZABLE writes fail closed instead of relying on stale snapshots. Owner IDs cannot be reassigned through these guarded tables. These changes need explicit maintenance compatibility review before installation.

Cleanup is a separate single transaction: lock the subject job, lock its subscriptions in endpoint order, delete its linked push_sent rows, delete subscriptions, commit counts and cleaned state. A failed later deletion rolls back earlier ledger deletion, keeping endpoint resolution available. The personal profiles/app_state/ai_usage rows remain until their already-existing auth cascade, so an Auth failure does not unnecessarily destroy preferences or reset the AI counter.

New NOT VALID CASCADE FKs protect future push_subscriptions owners and future push_sent endpoints. Installation neither validates nor deletes old orphans. Existing known original rows are preserved exactly in the integration fixture. FK constraints are not a substitute for current-owner/version checks when an endpoint is reused. The atomic record RPC supplies that check for matched new sender code. API-role TRUNCATE grants are narrowly revoked on these five tables because RLS and row triggers do not cover TRUNCATE; no current Data API TRUNCATE exploit is asserted. Service/admin maintenance remains available. DELETE is not blocked by the personal-write guards.

## Completion and limits

Completion checks that the auth user, owned profiles/app_state/ai_usage and subscriptions are absent. It does not claim all unknown historical endpoint or external-resource data are erased. Existing legacy orphan reconciliation is separate. Shared fixtures/predictions and shared AI output are not removed by account cleanup.

The accepted but **uninstalled** MM05 proposal's refunds cascade, work owner SET NULL and retained shared/reconciliation rows are covered as an exact FK-shape compatibility fixture. A separate root integration case installs the actual MM05 proposal with lifecycle SQL and verifies both new allocation and reserved dispatch are denied after deletion admission, without changing usage counts or making a provider call. Private work output remains NULL in that fixture. No blanket work/refund/reconciliation deletion, fake refund or quota reset is introduced. The local MM05 allocation/dispatch proposal now calls the optional lifecycle guard within its transactions; oldv17 isolation and a matched hosted deployment remain release gates.

This protocol does not revoke every previously issued JWT or prove private publisher-principal/session invalidation. Its current write guards cover only push_subscriptions, app_state and profiles; existing/new FKs provide related row-lifetime checks. Root must inspect any stronger source-publisher helper claims separately. External sender dispatch already in flight cannot be recalled. New sender code must check before dispatch, use atomic record after completion and preserve the existing cron-secret gate; old sender work must be paused/drained or isolated. A TTL, lease expiry or successful deploy response is not drain evidence.
