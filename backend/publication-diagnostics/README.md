# Private publication diagnostics - unexecuted proposal

These files build a project-specific SQL proposal from the three exact captured definitions of `schema_valid`, `payload_valid` and `materialize`. They contain no provider payload, user rows or full private source capture. Use `node backend/publication-diagnostics/build-candidate.mjs production <private-capture-directory> <new-output.sql>` or the separate `staging` profile. Each capture is SHA-256 checked; the generated transaction also checks the installed definitions before changing anything. Never apply a production candidate to staging or bypass drift checks.

The original boolean validators remain byte-identical and authoritative. A private invoker sidecar calls them, walks the fixed schema to identify a rejected field, and instruments the exact existing relational branches for fixed reasons. Unknown object names and map keys are masked; paths contain only schema-owned names and `[*]`/`.*`, with a 240-character cap. The diagnostic projection has protocol/profile, validator source SHA-256, acceptance flag, fixed code/path, canonical JSONB payload SHA-256, byte count and card count. It never returns a rejected value or raw exception text. The inspector is STABLE and checks current payload/schema definition hashes on every call; post-install drift returns VALIDATOR_SOURCE_DRIFT and the actual current payload-validator hash instead of claiming the old diagnostic contract still matches. This does not silently replace or relax the authoritative validator. Scalar reasons distinguish wrong type, length, control characters, schema pattern, date/timestamp, numeric range and integer requirements. Relational reasons cover duplicate cards, probability vectors, board identity/references/counts, Tips ranks/tabs/leg bounds, slip references, shared-record identity and staging competition/analysis relations.

The private schema and all functions deny PUBLIC/anon/authenticated. Only the existing service role and display materializer get USAGE/EXECUTE, and no definer privilege or public RPC is added. There is no table, row retention, data export, payload log, automatic retry or permission to raise any bound. The production patch corrects misleading bound text to the already-enforced 3000 cards / 4 MiB; staging keeps its separate contract. Full SQL/owner/default-privilege review is required before installation.

The exact materializer rejection emits SQLSTATE `MMV01` and places the bounded diagnostic in error DETAIL. It still raises an exception, so edition insertion/pruning and any same-transaction journal write roll back. No durable attempt journal is claimed. An approved outer caller/log sink must record the safe metadata after the failed statement, correlate its own attempt/run ID and apply a reviewed operational retention policy. PostgreSQL cron/hosted logging must be checked for DETAIL preservation; SQL completion/cron enqueue alone is not downstream completion evidence. Already accepted editions and immutable source claims are not modified by diagnosis.

Verification uses `node --test test/publication-diagnostics-sql.test.mjs`, exact original functions in a fresh pinned PostgreSQL 16.6 container, Docker's configured context, `--network none`, no host mounts, invented public fixture rows and only its own PID-named container cleanup. Tests compare unchanged validator hashes, valid/invalid nested/relational payloads and sanitizer output, role isolation, source-drift rejection, original generic failure versus new actual materializer DETAIL, successful publication and failed-publication rollback. This is local SQL evidence, not hosted cron logging, an explanation of the historical rejected payload, or deployment authorization.

Hosted source captures and the historical 28-failure incident remain separate owning evidence.
